Hand this to whoever is running the demo

Get it running, then show it in twelve minutes

Everything needed to take this repository from a fresh laptop to a live demonstration in front of a board — including what to click, what to say, and what to answer when they push back.

Before you start

What this is, in two sentences

A maintenance and production tracking system for a Greenlam laminate plant. Operators report breakdowns from a phone in thirty seconds, leadership sees where the plant is losing time, and the plant's existing Excel register can be imported and exported without anyone changing how they already work.

Every number you will see is synthetic. Ninety days of generated history — real structure, invented figures. Say this out loud early in the demo. If someone asks whether this is real plant data, the answer is no, and the seeding script physically refuses to write to a non-local database precisely so that stays true.

On a Mac, all four in one go:

# Homebrew — skip any you already have
brew install python@3.12 node postgresql@16 git
brew services start postgresql@16

On Ubuntu or WSL:

sudo apt update
sudo apt install -y python3.12 python3.12-venv nodejs npm postgresql git
sudo service postgresql start

There is a Docker path too — but read this first

If you have Docker Desktop installed and running, docker compose up starts the database, the API and the app together and you can skip most of the next section. Two warnings:

  • You need Docker Desktop, not just the docker command line — the CLI alone does not include the compose plugin this uses.
  • The native path below is the one verified end to end. The Docker path is written and the compose file is valid, but it was not run on the machine this was built on, so if it misbehaves fall back to the native steps rather than debugging Docker an hour before a board meeting.
cp .env.example .env
docker compose up
# then, in a second terminal, once it has settled:
docker compose exec api python -m app.seed

On Windows use the PowerShell scripts instead of the shell ones — setup.ps1 and run.ps1, run with powershell -ExecutionPolicy Bypass -File .\setup.ps1. They do the same checks and set the same secrets. They were written against the macOS versions but not executed on a Windows machine, so leave a little time the first time.

Setup · the verified path

Five steps to a running system

  1. Get the code and create the databases

    git clone <the repository URL> greenlam
cd greenlam

createdb greenlam
createdb greenlam_test   # only needed if you want to run the tests

    createdb not found? Postgres is installed but not on your PATH. On a Mac try export PATH="/opt/homebrew/opt/postgresql@16/bin:$PATH".

  2. Set up the API

    cd api
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

    This pulls FastAPI, SQLModel, Alembic and the Excel reader. Takes two or three minutes the first time.

  3. Set the three environment variables

    export DATABASE_URL="postgresql+psycopg://$USER@localhost:5432/greenlam"
export JWT_SECRET="local-dev-secret-padded-out-to-32-bytes-ok"
export PIN_PEPPER="local-dev-pepper-padded-out-to-32-bytes-ok"

    PIN_PEPPER must be the same value when you seed and when you serve. It is mixed into every PIN hash, so if you seed with one value and start the server with another, every sign-in fails with "Employee ID or PIN is incorrect" and nothing tells you why. This is the single most common way this setup goes wrong. Use the exact strings above and keep the terminal open.

  4. Create the tables and fill them with demo data

    .venv/bin/python -m alembic upgrade head
.venv/bin/python -m app.seed

    The seed prints every sign-in you can use. It creates 42 machines, 10 people, and 287 breakdowns spread across 90 days. Then start the server and leave this terminal running:

    .venv/bin/uvicorn app.main:app --port 8000

  5. Start the app in a second terminal

    # from the repository root, not from api/
npm install
npm run dev

    Open http://localhost:5173. You should see a sign-in screen with a Greenlam mark, a language switch and a theme switch.

Confirm it actually works before the meeting

  • Sign in as EMP002 / 573014. You should land on a floor screen headed "4 things need you".
  • Click Dashboard. You should see six numbers, a plant map, and four charts.
  • Click a block on the plant map. A strip should appear at the top with that machine's downtime, MTBF and reject rate together.
  • Scroll to Machine by machine and switch to Impregnation. It should report roughly a 44% higher reject rate on out-of-spec paper.
  • Click the हिं button top-right. The whole interface should turn Hindi within a frame.
  • Sign out and sign in as EMP004 / 746092. There should be no Dashboard tab.

All four working means the stack is healthy. Do this the night before, not five minutes before.

The demo · twelve minutes

What to click, and what to say

Four acts. Sign out between them — the sign-out is part of the story, because the point of act three is that different people see different things.

Have two browser windows open before you start: one at normal size, one narrowed to about a phone's width. You will switch to the narrow one in act one and it looks unprepared if you resize live.

  1. 0:00 – 3:00

    Act one · the floor

    sign in as EMP004 / 746092

    Open with the problem, not the product. "A press stops. Right now somebody walks to an office, finds a register, and writes a line in it. By the time anyone reads that line the press has been down a week."

    • Point at "4 things need you" — the app opens on what is wrong, not on a menu.
    • Switch to the narrow window. Tap Report a breakdown. Type p4 — Press-4 appears without picking a section first. Choose Critical, type "hydraulic pressure dropping", submit.
    • Say: "Three fields. The old form had seven, and the section had to be chosen before the machine list would even load."
    • Turn off wifi and tap something. An offline banner appears and the work is still saved.
    • Say: "Nothing on this screen waits for the network. A press hall has patchy wifi and that is a fact you design around, not a bug you file."
  2. 3:00 – 8:00

    Act two · the board

    sign out, sign in as EMP002 / 573014, click Dashboard
    • Let the headline land: "Where the plant is losing time — and where it is fine."
    • Point at the line under the six numbers: "Downtime cost needs an hourly rate per machine — not set yet, so no rupee figure is shown rather than a guessed one."
    • Say: "That sentence is the most important thing on this screen. Every dashboard you have ever been shown had a rupee figure on it. Ask where it came from." This is the line that wins the room.
    • Scroll to the plant map. Taller and darker blocks lost more time; the warm ones need attention now.
    • Scroll to "What causes the downtime". Hover across the bars — the tooltip follows. Say: "Four causes are 90% of it. That is next month's maintenance agenda, and it took no analysis."
    • Click the Mechanical bar. A strip appears at the top joining every dataset on the page for that one cause.
    • Scroll to "Which machines cost the most" and click Press-4. Same strip, now with its downtime, its failure count, its MTBF and its reject rate together.
    • Say: "Those five numbers live in four different charts. Nobody was ever going to hold them in their head at once."
    • Scroll to Production and quality and stop on the amber box.
    • Say: "This is the one that predicts instead of reports. Reject rate climbs on these machines before they fail. If that holds on real production, it is condition monitoring with no sensors and no capital."
  3. 8:00 – 10:00

    Act three · the thing that prevents a defect

    sign out, sign in as EMP004 / 746092

    Open by pointing at what is missing. "Same app. No Dashboard tab, no Import tab. Access is not a setting someone forgot to switch on — the tabs are not there."

    • Tap Log a paper roll.
    • Say: "This is the impregnator. Paper comes in as a roll, goes through a resin bath, gets dried, gets cut. Everything the plant makes starts here."
    • Type roll number R-DEMO-01, pick IMP-1, pick grade Decor 80 GSM.
    • In VC — volatile content, type 8.4.
    • Stop. Let them read the red box: "VC 8.4% is above the 7% maximum for Decor 80 GSM."
    • Say — this is the most important sentence in the demo: "Blistering shows up at the press, so the press gets blamed and re-plated. But it is mostly caused here — residual moisture flashes to vapour under the platen and lifts the layers. That number is the warning, and it is on screen while the roll is still on the floor."
    • Press Save roll. It saves.
    • Say: "It warns. It never blocks. The moment you force somebody to choose between an honest reading and finishing their shift, they stop entering honest readings — and then the whole thing is fiction."
  4. 10:00 – 12:00

    Act four · proving it, and the language

    sign out, sign in as EMP002 / 573014
    • Dashboard → scroll to Machine by machine. One row per machine: downtime on the left, scrap on the right.
    • Say: "A machine can be worst for two completely different reasons — it stops, or it makes scrap. Different fix, different owner, different budget. Nobody was ever going to hold four charts in their head to tell them apart."
    • Switch the toggle to Impregnation.
    • Read the finding aloud: "Sheets from paper inside its spec window reject at 3.75%. From paper outside it, 5.41% — 44.3% higher."
    • Say: "That is the hypothesis tested against the plant's own numbers. If it had come back the other way, the number would say so — it is reported as a comparison, not a claim."
    • Point at IMP-1: 26% of its rolls out of spec, against 4–5% everywhere else.
    • Click हिं. The whole interface turns Hindi — headings, alerts, section names, chart labels.
    • Click HI for Hinglish. Say: "This is how a plant floor actually talks. Many operators read Latin script faster than Devanagari even when Hindi is their first language."
    • Point out Press-4 stays Press-4. "Machine codes are painted on the machine. Translating them would send a technician to an asset that is not labelled that way."
    • If there is time: Import → drop docs/sample-breakdown-register.xlsx → then drop it again. It creates zero.
    • And: Lists → this is where the plant replaces every placeholder design, size, grade and supplier with their own. Say: "None of these values are Greenlam's. They are here so the forms work — the first job on day one is replacing them, and that is a screen, not a support ticket."
    • And the one to end on if a finance person is in the room: Setup. Both counters read 0 / 33. Say: "Every rupee figure on the dashboard is switched off right now, because nobody has told this system what an hour of downtime costs. It will not guess."
    • Type 38000 and 16 into the two boxes, press each Apply to all, then go back to Dashboard. The withheld line has become a total, and availability has moved off calendar hours onto the real schedule. Say: "Three answers from you, and the board gets numbers it can defend. Until then it gets a sentence explaining what is missing."

    Close on this: "Everything else in here records what already went wrong. The impregnation screen records the thing that causes it — and tells somebody while there is still time to act."

Hard questions

What the panel will ask

They askYou say
"Is this real data?"No. Ninety days generated with realistic structure. The seeding script refuses to write to any non-local database until plant IT approves hosting in writing.
"What does downtime cost us?"The system will not guess. It needs an hourly rate per machine — one costing exercise, about a day. The arithmetic is already written and switched off until then.
"Why not just buy MaintainX or Limble?"They are good and they are asset-centric — they model a machine and a work order. In laminate, blistering mostly originates at impregnation, not at the press where you see it. An asset-centric tool logs that as a press defect for ever and re-plates the wrong machine.
"Will operators actually use it?"Thirty seconds and three fields, in their own language, works offline. And it is measured — the system records whether a ticket was raised by scan or by typing, so adoption is a number rather than an opinion.
"Are you tracking individual performance?"A person sees their own figures. Someone holding the dashboard sees the team, compared to the team average and listed alphabetically — never ranked. Two people on the floor cannot see each other's numbers at all; that is enforced in the code, not in a policy document.
"Who gets the dashboard?"Whoever you name — several people, not one. Everyone else gets the app, which is the whole floor. There is no middle tier and no per-section scoping to maintain.
"What is RC and VC, and why should I care?"Resin content and volatile content in the impregnated paper. High volatiles flash to vapour under the press platen and lift the layers — that is a blister. It is the one number here that predicts a defect instead of counting one, and nothing in the plant's data had it before.
"How do you know the paper is the cause?"We don't assert it, we measure it. The dashboard compares reject rate on sheets pressed from in-spec paper against out-of-spec paper. On this data it is 3.75% against 5.41%. If it had come back level, the screen would say that.
"What happens to our Excel register?"It keeps working. This reads it and writes it back out nightly with the same column headers, quirks included, so existing pivot tables do not break.
"What if the internet goes down?"The floor app keeps working and queues everything locally. It reconciles when signal returns, and that reconciliation is tested against three devices going offline and disagreeing.
"How much does it cost to run?"Free tiers today — the hosting, the database and the nightly job all fit. Compare with roughly $35–75 per user per month for a commercial platform.
"What is NOT built?"Be straight about it: no rupee costs yet, availability is calendar-based and says so, machine criticality is unset, and the predictive quality signal is a hypothesis on synthetic data. All four are listed on screen, not hidden.

If something breaks

Troubleshooting

SymptomFix
"Employee ID or PIN is incorrect" for every accountAlmost always PIN_PEPPER differing between the seed run and the server. Set it, re-run python -m app.seed --reset, restart the server in the same terminal.
Sign-in page loads but nothing happensThe API is not running. Check the first terminal; visit http://localhost:8000/api/health.
createdb: command not foundPostgres is not on your PATH. Mac: export PATH="/opt/homebrew/opt/postgresql@16/bin:$PATH"
connection refused on port 5432Postgres is not started. brew services start postgresql@16 or sudo service postgresql start.
Dashboard is emptyThe seed did not run, or ran against a different database. Re-run .venv/bin/python -m app.seed --reset.
Charts look tiny or squashedHard-refresh (Cmd/Ctrl + Shift + R). The charts measure their container on mount and a cached stylesheet can beat them to it.
Hindi shows as boxesThe Devanagari font did not load. Hard-refresh; if it persists, npm install did not complete — run it again from the repo root.
Port 5173 or 8000 already in uselsof -ti:5173 | xargs kill -9 (or 8000), then start again.

The one thing to do before you present

Run the whole setup once, end to end, on the machine you will actually present from, the day before. Not the same machine you tested on. Not the morning of. Every failure in the table above takes two minutes to fix the night before and ends a demo if it happens in the room.
